# Doctrine Follow-up — fixes for two issues

## Issue 1 — Meta-language bleed into client emails

**Root cause:** `original_body_summary` was being populated with meta-language ("Pitched a performance-based service, citing competitor growth, as urgency"), then pasted directly into the fallback template's `"Following up on my previous email about {summary}"` line. The live critic/rewriter loop never ran on the fallback path.

**Self-healing guards added:**

1. `sanitizeSummary()` in `emailSummarizer.ts` now iteratively strips meta-participles (20-verb list) anywhere in the sentence, kills `the ability to drive X` constructions, kills `as urgency / as social proof / as a benchmark` tails. Runs up to 5 passes until output stabilizes.
2. `generateFollowupEmail()` re-sanitizes `ctx.original_body_summary` before it reaches any LLM prompt. Older contaminated DB rows get cleaned on read — no migration needed.
3. `buildFallbackFollowup()` checks the summary post-sanitize. If meta is still detected, it drops the topic entirely and uses the topic-less `"Following up on my previous email."` line rather than bleeding meta to the inbox.
4. `detectMetaLanguage()` now catches `claiming the ability to drive`, bare `the ability to [verb]`, and more participles (`suggesting`, `arguing`).

**Test it:** trigger a follow-up for a prospect whose `original_body_summary` contains meta-language. The logs will show `Self-healed meta-contaminated original_body_summary before generation` with before/after.

## Issue 2 — "Stage X already exists" + test mode removal

**Root cause of the error:** `followups` has a unique constraint `uq_followups_prospect_stage` on `(prospect_id, stage)`. The original `/followup-now` loop read `max(stage)` from sent follow-ups only, then raced any queued row already sitting in that slot. Postgres returned a unique-violation that bubbled to the UI as `"Stage 2 already exists"`.

**Fix:** `/followup-now/:prospectId` now:
- Counts ALL stages (queued, generating, pending_approval, sent, failed, cancelled) when picking next.
- Bumps stage by 1 on every conflict (no DB re-read).
- 50-attempt ceiling — effectively unlimited for normal use.

**Test mode removal:** Every code path now treats all prospects as production:
- `cron.ts` — dropped the test-mode tick and `autoQueueNextStages()` call.
- `scheduler.autoQueueNextStages()` — now a no-op (kept for import compat).
- `scheduler.autoQueueAllCampaigns()` — ignores `batchLabel`, always uses the user's production timing window.
- `doctrine.partitionAndSchedule()` and `getUserTimingSettingsForProspect()` — no longer branch on `TEST_MODE_LABEL`.
- `doctrine.ts` routes `/prospect/:id/campaign-type`, `/campaign/queue`, `/campaign/launch` — force-normalize `campaign_type` to `"production"`. If a legacy caller passes `"test"`, response includes `normalized_from: "test"` so you can see it in logs.
- Dashboard UI already had the Test Mode checkbox hidden (`display: "none"` on accounts.tsx:339) — no UI changes needed.

**DB is untouched** — `testMode` column and any existing `batchLabel = "followup app test"` rows stay in Postgres, just ignored. Safe zero-downtime deploy.
